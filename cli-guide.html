03 — DATA & PERSISTENCE
프로세스는 끝나도, 파일은 남습니다.
데이터베이스 대신 UTF-8 JSONL 파일을 사용합니다.
저장 위치
기본값은 실행 위치의 ./data
패키지 폴더 기준이 아니라 명령을 실행한 디렉터리 기준입니다. 각 명령 뒤의 --data-dir 경로로 다른 폴더를 선택할 수 있습니다.
transactions.jsonl
거래 한 건당 한 줄. ID·날짜·유형·금액·카테고리·메모·태그를 저장합니다.
categories.jsonl
등록된 카테고리 이름. 거래 추가·카테고리 변경 시 등록 여부를 확인합니다.
budgets.jsonl
월과 예산 금액. 월 요약에서 해당 월 예산과 지출을 비교합니다.
Storage 생성 시 폴더와 세 파일을 준비하고, 카테고리 파일이 비어 있으면 food·transport·rent·salary·etc를 씁니다. 조회 명령도 이 초기화 과정을 거칩니다.
데이터의 모양
파일의 JSON ↔ 메모리의 객체
저장소가 JSON 한 줄을 읽으면 Transaction.from_record()가 검증해 거래 객체로 바꿉니다. 저장할 때는 to_record()로 딕셔너리로 바꾸고 JSON으로 씁니다.
{"id":"TX-예시","type":"expense","date":"2026-10-25","amount":4500,"category":"food","memo":"커피","tags":["coffee"]}
위는 형식 설명용 가상 레코드입니다. 실제 새 ID는 TX-와 UUID로 생성합니다. 금액은 양수 정수이며 수입·지출 구분은 type이 맡습니다.
추가 / import거래 파일 끝에 한 줄씩 추가
수정 / 삭제전체 순회 → 임시 파일 → 원본에 복사
카테고리 / 예산 변경목록을 읽고 변경 후 전체 다시 쓰기
수정·삭제의 임시 파일은 검증 중 원본을 보존하기 위한 준비 단계입니다. 원자적 파일 교체나 백업이 아니므로, 원본 복사 중 장애까지 보호하는 구조는 아닙니다.



04 — ERRORS & EXIT
문제가 생기면 어느 경로로 돌아올까?
일반 결과는 stdout, 오류와 해결 힌트는 stderr로 출력합니다.
↻
대화형 입력 검증 → 다시 질문
add의 날짜·유형·카테고리·금액은 _ask() 안에서 검증합니다. AppError가 나면 오류와 힌트를 보여주고 해당 항목을 다시 묻습니다.
모든 입력이 재질문되는 것은 아닙니다. 카테고리 추가·삭제는 입력을 한 번 받은 뒤 서비스로 넘깁니다.
exit 1
작업 실패 → 공통 오류 안내
handle_cli_errors가 run_cli를 감쌉니다. AppError, 입력 중단, 파일·인코딩 오류 등을 안내하고 1을 반환합니다.
CSV 가져오기에서 행을 건너뛴 경우도 CLI가 1을 반환합니다. 이때 정상 행은 이미 저장될 수 있습니다.
exit 0 / 2
정상 완료와 인자 오류
일반적인 정상 완료와 --help는 0입니다. 명령 누락·알 수 없는 옵션 등 argparse 단계 오류는 2입니다.
__main__.py는 반환된 코드를 SystemExit에 전달합니다. 파서의 SystemExit는 공통 오류 데코레이터에 잡히지 않고 바로 전파됩니다.
같은 잘못된 금액도 전달 위치에 따라 경로가 다릅니다. list --limit 0은 파서에서 종료 코드 2, budget set --month 2026-10 --amount 0은 서비스 검증에서 종료 코드 1입니다.



05 — GENERATORS & STREAMING
전부 담아두지 않고, 필요할 때 하나씩.
제너레이터는 생산 방식, 스트리밍은 처리 방식입니다.


정의와 사용 이유
제너레이터와 스트리밍
제너레이터(generator)는 값을 필요할 때 하나씩 만들어 내는 이터레이터입니다. 이터레이터는 next()로 다음 값을 요청할 수 있는 객체이고, for문이 이 요청을 대신 반복합니다. 리스트처럼 모든 결과를 미리 만들 필요가 없습니다.
스트리밍(streaming)은 데이터를 작은 단위로 읽고 처리해 다음 단계로 넘기는 방식입니다. 이 CLI에서는 네트워크 전송이 아니라, 파일의 행을 순서대로 처리하는 것을 뜻합니다. 제너레이터는 이 흐름을 구현하는 수단 중 하나입니다.
사용 이유: 거래가 많아져도 원시 거래 전체를 리스트로 보관하는 부담을 줄이고, 읽기·검증·처리를 연결할 수 있습니다. 단, 소비하는 쪽에서 list(...)로 모으면 다시 전체 결과만큼 메모리를 사용합니다.
하나씩 읽는다고 파일을 덜 읽는 것은 아닙니다. 최신순 선택이나 월 집계는 전체 파일을 확인해야 결과를 결정할 수 있습니다.


yield의 역할
값을 건네고, 멈춘 자리에서 이어가기
yield는 함수가 아니라 파이썬 키워드입니다. 일반적인 def 안에 yield가 있으면 제너레이터 함수가 됩니다. 함수를 호출하면 본문이 바로 실행되는 대신 제너레이터 객체를 반환합니다.
# repositories.py의 핵심 흐름을 축약한 예시
for line_number, record in _iter_jsonl(self.path):
    yield line_number, Transaction.from_record(record)
소비자가 다음 값을 요청하면 다음 yield까지 실행합니다. yield는 값을 넘긴 뒤 지역 변수와 실행 위치를 유지한 채 멈추고, 다음 요청에서 이어갑니다. return이나 함수의 끝을 만나면 순회가 끝납니다.
일반 함수의 return은 결과를 돌려주고 호출을 끝냅니다. yield는 여러 번 값을 건네는 중간 정지점입니다. 이 CLI의 _iter_jsonl(), iter_transactions(), search_transactions()가 이 방식을 사용합니다.


이 CLI에서 실제로 이어지는 흐름
파일 한 줄→JSON 해석→Transaction 검증→서비스에서 선택·집계→출력 또는 CSV 기록
명령마다 스트리밍을 활용하는 범위가 다릅니다.
경로처리 방식기억할 점
저장소 읽기행을 읽어 검증한 거래를 하나씩 yield요청한 만큼 진행하며, 저장 데이터 오류도 순회 중 발생할 수 있음
list전체를 순회하며 최신 N건 선택 → 리스트 반환원시 거래 전체 대신 선택할 N건을 유지하지만, 출력 전 전체 확인 필요
search최신순 최대 256건 선택 → 하나씩 yield → 다음 묶음 선택첫 결과 전에도 전체 순회가 필요하며, 다음 묶음에서 파일을 다시 읽음
summary / export순회하며 집계 / 조건에 맞는 행을 CSV로 기록summary는 합계·카테고리 집계를 유지하고, export는 파일 순서로 기록
검색 제너레이터를 만드는 것만으로 검색이 끝나지는 않습니다. CLI의 _print_transactions()가 for문으로 소비할 때 검증·파일 순회·yield가 실제로 진행됩니다.



06 — TYPE HINTS
타입힌트는 모듈 사이의 데이터 안내문입니다.
어떤 값을 받고 무엇을 돌려주는지 선언합니다.


정의와 사용 이유
입력과 출력의 모양을 읽는 방법
타입힌트(type hint)는 변수·매개변수·반환값에 기대하는 타입을 적는 표기입니다. 값: 타입은 입력·변수에, -> 타입은 함수의 반환값에 붙습니다.
def validate_amount(value: str | int) -> int:
이 선언은 “문자열 또는 정수를 받아 정수를 반환한다”는 뜻입니다. 함수 본문을 읽기 전에 입출력 관계를 파악할 수 있습니다. 이 함수는 유효하지 않은 값이면 정수를 반환하는 대신 AppError를 발생시킵니다.
사용 이유: CLI의 문자열 입력이 서비스에서 어떤 값으로 바뀌는지, 저장소가 어떤 객체를 전달하는지 추적하기 쉬워집니다. IDE 자동완성과 정적 타입 검사 도구의 오류 탐지에도 도움을 줍니다.
검증과의 차이
표기만으로 입력이 검사되지는 않습니다.
파이썬은 보통 타입힌트를 실행 중에 자동 강제하지 않습니다. amount: int라고 적었다고 “양수만 허용”하거나 문자열이 자동으로 정수로 변환되지는 않습니다.
실제 데이터 검사는 validators.py, 저장 레코드 검사는 Transaction.from_record(), 카테고리 등록 여부 같은 업무 규칙은 서비스가 수행합니다.
타입힌트는 “기대하는 값의 종류”, 검증 코드는 “실제로 허용할 값의 조건”을 담당합니다. int 타입만으로 0보다 커야 한다는 규칙까지 표현하지는 않습니다.


이 코드베이스에서 자주 보이는 표기
표기읽는 법이 CLI에서의 의미
str | int문자열 또는 정수금액은 입력 문자열이나 이미 변환한 정수로 받을 수 있음
int | None정수 또는 값 없음월 예산이 있으면 금액, 없으면 None
list[Transaction]거래 객체를 담은 리스트list_transactions가 선택한 최신 거래 목록
Iterator[Transaction]거래를 하나씩 꺼낼 수 있는 이터레이터search_transactions의 지연 실행 결과. 이 표기 자체가 제너레이터를 만드는 것은 아님
Iterable[Transaction]거래를 순회할 수 있는 대상_print_transactions는 리스트와 제너레이터 모두 받아 출력 가능
Sequence[str] | None문자열 시퀀스 또는 Nonerun_cli에 인자 목록을 전달하거나, None으로 실제 명령줄 인자를 사용
Callable[[str], T]문자열을 받아 T를 돌려주는 함수_ask에 검증 함수를 전달. TypeVar로 선언한 T는 검증 함수의 반환 타입과 _ask의 반환 타입을 연결
-> None유의미한 반환값 없음append처럼 결과 객체 대신 파일 저장이라는 작업을 수행



07 — JSONL vs CSV
내부에는 JSONL, 외부와 주고받을 때는 CSV.
둘 다 텍스트 형식이지만 표현 방식과 쓰임이 다릅니다.


JSON Lines
JSONL · 한 줄에 JSON 값 하나
JSONL은 줄마다 독립된 JSON 값을 담는 형식입니다. 이 앱은 각 줄을 JSON 객체로 제한합니다. 파일 전체를 하나의 JSON 배열로 감싸지 않습니다.
{"category":"food","amount":4500,"tags":["coffee"]}
{"category":"transport","amount":1500,"tags":[]}
형식 비교용 축약 예시입니다. 실제 거래 저장 시에는 ID·유형·날짜·메모 등의 필드도 필요합니다.
장점: 필드 이름이 각 행에 있고 숫자·배열 등 JSON 타입을 표현할 수 있습니다. 한 줄씩 읽거나 끝에 레코드를 추가하기 쉽습니다. 태그 목록을 배열로 그대로 보관할 수 있습니다.
단점: 필드 이름이 반복되어 파일이 길어지고, 스프레드시트에서 바로 다루기에는 불편합니다. 특정 ID 검색이나 수정 기능이 형식 자체에 있지는 않아 이 앱은 파일을 순회하거나 다시 씁니다.
Comma-Separated Values
CSV · 행과 열로 표현한 표
CSV는 보통 쉼표로 열을 구분하는 표 형태의 텍스트입니다. 이 앱은 헤더로 열 이름을 표시하고 날짜·유형·카테고리·금액·메모·태그를 주고받습니다.
date,type,category,amount,memo,tags
2026-10-25,expense,food,4500,커피,"coffee,morning"
쉼표가 들어간 필드는 큰따옴표로 감쌉니다. 따옴표와 줄바꿈도 이스케이프 규칙이 있어 단순히 split(',')로 읽으면 안 됩니다.
장점: 스프레드시트와 여러 도구 사이에서 표 데이터를 교환하기 좋습니다. 열 이름을 매 행 반복하지 않아 평평한 표를 간결하게 표현합니다. 행 단위 처리에도 사용할 수 있습니다.
단점: 숫자·날짜·배열의 타입을 자체적으로 명확히 담지 못합니다. 가져오는 쪽의 해석·변환이 필요하고, 태그 배열처럼 복합적인 값은 문자열로 펼칠 규칙이 필요합니다.


코드베이스에서 두 형식을 나눈 이유
비교JSONL · 내부 저장CSV · 가져오기·내보내기
읽고 쓰는 주체repositories.py의 JSONL 저장소services.py의 csv.DictReader / csv.writer
값의 모양금액은 JSON 숫자, tags는 JSON 배열가져올 때 텍스트를 검증·변환하고 tags는 쉼표로 분리
거래 IDID를 저장해 수정·삭제에 사용CSV 스키마에 ID 없음. 가져올 때 새 ID 생성
줄과 레코드물리적인 한 줄이 JSON 값 하나따옴표로 감싼 필드에 줄바꿈이 있으면 한 레코드가 여러 줄일 수 있음
데이터 교환 범위거래·카테고리·예산을 별도 파일에 보관거래만 교환. 카테고리는 미리 등록되어 있어야 하며 예산은 포함하지 않음
이 앱에서 export → import는 원본 저장소를 그대로 복원하는 백업 절차가 아닙니다. ID가 새로 만들어지고, 카테고리와 예산 설정은 별도로 관리됩니다. 두 형식 모두 파일 형식만으로 업무 규칙이나 저장의 원자성을 보장하지는 않습니다.
